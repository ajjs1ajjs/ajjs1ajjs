## 1. Executive Summary

## 2. Опис і карта проєкту

У відстежуваному дереві є три файли:

- `README.md` — профіль, стек навичок і зовнішні посилання на портфоліо, DIST Hub, email та Telegram.
- `.github/workflows/link-check.yml` — перевіряє Markdown-посилання у README на `push` до `main`, `pull_request` до `main`, за розкладом щопонеділка та вручну.
- `.gitattributes` — задає нормалізацію кінців рядків.

Потік виконання: GitHub event → Ubuntu runner → `actions/checkout` → `lycheeverse/lychee-action` → перевірка URL з `README.md`. Workflow не збирає і не розгортає застосунок.

## 4. Детальні знахідки

### CI та якість

#### A-01 — Link check не блокує помилкові посилання

- **Категорія:** CI / документація
- **Пріоритет:** P2
- **Поточний стан:** workflow перевіряє тільки `./README.md` на push, PR, за розкладом і вручну.
- **Проблема:** `fail: false` явно вимикає провал workflow при помилці lychee. Тому PR може змінити або додати неробоче посилання й залишитися зеленим; регулярний запуск теж лише повідомляє про помилку.
- **Докази:** `.github/workflows/link-check.yml`, рядок `fail: false`; `args` обмежує перевірку одним README.
- **Рекомендація:** якщо справність посилань є вимогою до змін README, встановити `fail: true` для PR/push. Для scheduled workflow можна залишити не блокуючу звітність, але додати явний канал сповіщення, якщо він потрібен. Переконатися, що нестабільні сторонні сайти й обмеження rate limit не створюють хибних блокувань.
- **Заміна:** не потрібна.
- **Обґрунтування:** використовуваний Action підтримує обидві поведінки; чинне `fail: false` означає саме «не провалювати workflow при помилці».
- **Очікуваний результат:** неробочі посилання в PR стають видимими як контрольована помилка.
- **Ризики:** деякі сторонні сайти блокують автоматизовані запити або нестабільно відповідають; знадобляться винятки чи налаштування повторів.
- **Складність:** мала.
- **Залежності:** рішення щодо того, чи є посилання блокувальною вимогою.
- **Критерії готовності:** тестовий PR із навмисно некоректним URL завершується очікуваною помилкою; справний README проходить перевірку.
- **Упевненість:** висока.

### Безпека ланцюга постачання та дозволи workflow

#### A-02 — Не зафіксовано мінімальні права токена та immutable ревізії Actions

- **Категорія:** безпека / DevOps
- **Пріоритет:** P3
- **Поточний стан:** workflow не містить явного блоку `permissions`; Actions викликаються за major-тегами `@v4` і `@v2`.
- **Проблема:** фактичні дозволи `GITHUB_TOKEN` можуть залежати від налаштувань репозиторію/організації, а major-тег є рухомим посиланням на код Action. Для простого job достатньо явно обмежити токен читанням вмісту та посилити відтворюваність ланцюга постачання.
- **Докази:** весь `.github/workflows/link-check.yml`; GitHub документує `permissions` як спосіб прибрати непотрібні дозволи. Lychee Action рекомендує фіксацію до SHA та автоматизоване оновлення Actions.
- **Рекомендація:** додати `permissions: contents: read` на рівні workflow/job. Розглянути закріплення Actions за перевіреними повними SHA та налаштувати Dependabot для `github-actions` або інший регулярний процес контрольованого оновлення.
- **Заміна:** рухомі major-теги → повні SHA з коментарем версії (необов'язкове посилення безпеки).
- **Обґрунтування:** обмежує наслідки компрометації workflow та зменшує ризик непомітної зміни Action без зміни файлу.
- **Очікуваний результат:** мінімальні права та краще відтворюване CI.
- **Ризики:** SHA треба регулярно оновлювати; без автоматизації pin може застаріти. Немає доказу, що поточні теги скомпрометовані.
- **Складність:** мала.
- **Залежності:** перевірити політику дозволів GitHub у налаштуваннях репозиторію; вибрати спосіб оновлення SHA.
- **Критерії готовності:** у workflow явно задано лише необхідні permissions; версії Actions оновлюються контрольовано; job продовжує проходити.
- **Упевненість:** висока щодо наявних налаштувань; низька щодо фактичного обсягу токена без доступу до GitHub settings.
